# Risk Limits, Events, and Enforcement Boundaries

## Purpose

This document explains what the simulation's risk controls currently report, how risk events reach the Gateway, and what must not be inferred from a reported breach.

> **Scope:** This repository is an educational trading simulation. It is not connected to an exchange and does not execute real financial trades.

## Configured limits

The analytics service currently exposes these default risk limits:

| Limit | Default | Meaning |
|---|---:|---|
| Maximum position | 1,000 units | Maximum permitted absolute position under the evaluator's position rule |
| Maximum position value | 100,000 | Maximum permitted position value under the evaluator's valuation rule |
| Maximum drawdown | 1,000 | Drawdown threshold |
| Maximum daily loss | 500 | Daily-loss threshold |
| Warning ratio | 80% | Threshold ratio used to warn before a configured limit is reached |

These are application defaults, not a statement that every running container is using them. Environment/configuration overrides and the image actually deployed must be checked when diagnosing a runtime.

## Risk states and events

Risk evaluation can report the following states:

- `ok`: no configured limit is currently reported as breached or in warning.
- `warning`: a configured limit has reached its warning threshold.
- `breached`: one or more configured limits have been exceeded.

Risk events are generated by analytics and forwarded to the Gateway. The Gateway logs accepted risk events and exposes the latest analytics state through `GET /api/v1/analytics`. The dashboard can display this state; it is a reporting path.

Risk event types include:

- `RISK_LIMIT_WARNING`
- `RISK_LIMIT_BREACHED`
- `RISK_LIMIT_RECOVERED`

A breach may produce events for multiple limit types. While a violation persists, repeated event notifications may appear in the logs; inspect event-generation and transition semantics before interpreting each log line as a distinct new breach.

## Detection is not enforcement

**A `breached` status is evidence of risk detection, not proof that the matching engine has stopped accepting or executing orders.**

The analytics pipeline evaluates completed trade data and reports risk state. That reporting path alone does not guarantee that a new order is rejected before it can reach the matching engine.

Until pre-trade enforcement is implemented and verified at the authoritative order-admission or execution boundary, do not describe the current analytics risk status as a trading halt, kill switch, or guarantee that limits cannot be exceeded.

A future enforcement implementation should:

1. Check proposed orders against applicable limits before admitting them to the engine.
2. Define whether the rule evaluates the resulting position/exposure, not only the current position.
3. Specify which limits reject individual orders and which trigger a simulation-wide halt.
4. Make breach, rejection, halt, and recovery transitions explicit and observable.
5. Define an explicit recovery/resume policy rather than silently resuming after a transient status change.
6. Test boundary values, concurrent/order bursts, partial fills, long and short positions, valuation changes, daily rollover, and recovery.
7. Keep the analytics event stream and dashboard as observability surfaces, not the sole enforcement mechanism.

## Runtime verification

Start with service state and dependency readiness:

```bash
docker compose ps
curl -sS http://localhost:8080/api/health
curl -sS http://localhost:8080/api/ready
```

Inspect recent risk-event delivery:

```bash
docker compose logs --since=5m analytics gateway \
  | grep -Ei 'RISK_LIMIT|risk.limit|risk_event|risk.*(warning|breach|recover)' \
  | tail -n 60
```

Inspect the latest analytics state:

```bash
curl -sS http://localhost:8080/api/v1/analytics | python -m json.tool
```

Confirm the analytics image contains the expected configuration when source changes are not reflected in runtime:

```bash
docker compose build analytics
docker compose up -d analytics
```

Rebuilding/recreating a service can reset in-memory streaming state. Do not assume that pre-restart in-memory position, P&L, peak equity, or drawdown values survive a restart; verify persistence and startup/replay behavior separately.

## Incident interpretation example

A runtime snapshot observed on 2026-10-09 returned `riskStatus: "breached"`, position `2225`, equity `-11847.11`, and drawdown `21977.63`. Gateway logs also showed accepted risk events for `max_position`, `max_position_value`, `max_drawdown`, and `max_daily_loss`.

That snapshot demonstrated that risk reporting and event delivery were active while metrics were outside configured limits. It did **not** demonstrate that new trades were blocked. Runtime values are a diagnostic example, not a fixed expected result or a benchmark.

## Acceptance criteria for risk enforcement

Do not mark enforcement complete until automated tests demonstrate that:

- An order that would breach a hard pre-trade limit is rejected before execution.
- An order within all hard limits remains admissible.
- Position and position-value boundaries are tested at, below, and above the limit.
- Drawdown and daily-loss halt policies are explicitly defined and tested.
- A breach produces a traceable reason and structured log/event.
- Recovery requires the documented policy and cannot accidentally bypass the limit.
- Restart behavior and in-memory state recovery are documented and tested.
- End-to-end tests confirm that the engine does not execute an order rejected by risk controls.
