# Data Model and Event Contracts

## 1. Purpose

This document defines the logical data model and event contracts exchanged between the C++ trading engine, Python analytics service, Node.js gateway, and React dashboard.

The model is designed to be transport-independent.

JSON is the primary representation for the MVP. The same logical schema may later be represented using Protocol Buffers without changing the underlying business semantics.

The document also defines the data contracts currently implemented by the Python analytics service, including:

* Market ticks.
* Trade events.
* Analytics results.
* VWAP.
* SMA.
* EMA.
* Rolling price-return volatility.

Position, PnL, risk, gateway, and production streaming contracts are documented at the logical-contract level where their implementation is still planned.

---

## 2. Identifier Rules

All externally visible events should contain:

* `event_id`
* `timestamp`
* `event_type`

Orders contain:

* `order_id`
* `client_order_id` where relevant.

Trades contain:

* `trade_id`
* `buy_order_id` where available.
* `sell_order_id` where available.

Identifiers must be unique within the simulation session.

Recommended formats:

```text
evt-000001
ord-000001
trd-000001
```

The exact identifier-generation mechanism is an implementation concern, but consumers must treat identifiers as opaque values.

## 4. Order

An order represents an instruction submitted to the trading engine.

Example:

```json
{
  "order_id": "ord-000001",
  "symbol": "SIM",
  "side": "BUY",
  "type": "LIMIT",
  "price": 101.25,
  "quantity": 100,
  "remaining_quantity": 60,
  "status": "PARTIALLY_FILLED",
  "sequence": 42,
  "timestamp": "2026-09-07T12:00:00.100Z"
}
```

### 4.1 Validation Rules

The order contract requires:

* Price must be positive for a limit order.
* Quantity must be a positive integer.
* Side must be supported.
* Symbol must be valid.
* Sequence must be monotonically increasing.
* Remaining quantity must not be negative.
* Remaining quantity must not exceed the original quantity.

The detailed order implementation belongs to the C++ trading engine.

## 5. Trade

A trade represents an authoritative execution generated by the matching engine.

Example:

```json
{
  "event_type": "TRADE",
  "event_id": "evt-000123",
  "trade_id": "trd-000045",
  "symbol": "SIM",
  "price": "101.25",
  "quantity": 40,
  "taker_order_id": "ord-000010",
  "maker_order_id": "ord-000009",
  "taker_side": "BUY",
  "buy_order_id": "ord-000010",
  "sell_order_id": "ord-000009",
  "timestamp": "2026-09-07T12:00:01.000Z"
}
```

`taker_side` is the side of the order that crossed the spread. Taker and maker
identify who initiated the execution, not the direction of the fill, so
`buy_order_id` and `sell_order_id` are only well defined together with
`taker_side`:

```text
taker_side = BUY   ->  buy_order_id = taker, sell_order_id = maker
taker_side = SELL  ->  buy_order_id = maker, sell_order_id = taker
```

The trade event is authoritative for downstream analytics.

Analytics consumers must not reconstruct executed trades from order-book state when an authoritative `TRADE` event is available.

### 5.1 Python Trade Model

The Python analytics service represents trades using the `Trade` domain model.

Required fields:

```text
event_id
event_type
trade_id
symbol
price
quantity
timestamp
taker_side
```

Optional fields:

```text
buy_order_id
sell_order_id
taker_order_id
maker_order_id
```

The Python model validates that:

* `event_id` is not empty.
* `event_type` is exactly `TRADE`.
* `trade_id` is not empty.
* `symbol` is not empty.
* `price` is positive.
* `quantity` is positive.
* `taker_side` is `BUY` or `SELL`.

The parser derives `buy_order_id` and `sell_order_id` from `taker_side`;
a TRADE payload without `taker_side` is rejected.

Financial prices are represented internally using `Decimal`.

A book level represents aggregated liquidity at a single price.

Example:

```json
{
  "price": 101.25,
  "quantity": 250,
  "order_count": 4
}
```

A book snapshot can be represented as:

```json
{
  "event_type": "BOOK_UPDATE",
  "symbol": "SIM",
  "bids": [
    {
      "price": 101.00,
      "quantity": 200,
      "order_count": 3
    }
  ],
  "asks": [
    {
      "price": 101.25,
      "quantity": 250,
      "order_count": 4
    }

}
```

The C++ order book is the authoritative source for book state.

The Python analytics service does not currently require a book snapshot for the Phase 3.3 technical-indicator calculations.

## 10. VWAP

Volume Weighted Average Price is calculated over a collection of price and quantity observations.

The formula is:

$$
VWAP = \frac{\sum(P_i Q_i)}{\sum Q_i}
$$

where:

* `P_i` = price of observation `i`.
* `Q_i` = quantity of observation `i`.

### 10.1 Python Implementation

The Python analytics service provides:

```text
calculate_vwap(prices, quantities)
```

The implementation:

1. Materializes the input iterables.
2. Validates that the input is not empty.
3. Validates that prices and quantities have equal lengths.
4. Validates that every quantity is positive.
5. Calculates total traded quantity.
6. Calculates total traded value.
7. Divides total value by total quantity.

The implementation uses `Decimal` arithmetic.

### 10.2 Invalid Input

The function raises `ValueError` when:

* The input is empty.
* Prices and quantities have different lengths.
* A quantity is non-positive.
* Total quantity is not positive.

### 10.3 Precision

The calculation must not use integer division.

Financial calculations use `Decimal` to avoid unnecessary binary floating-point rounding.

## 11. SMA

Simple Moving Average is calculated over the latest `N` price observations.

The formula is:

$$
SMA_N = \frac{x_1+x_2+\cdots+x_N}{N}
$$

where `N` is the requested period.

### 11.1 Python Implementation

The Python analytics service provides:

```text
calculate_sma(prices, period)
```

The current implementation:

1. Converts the input iterable to a list.
2. Validates that `period` is positive.
3. Validates that prices are present.
4. Returns `None` if fewer than `period` observations exist.
5. Selects the latest `period` observations.
6. Calculates their arithmetic mean using `Decimal`.

### 11.2 Insufficient Data

If:

```text
number of prices < period
```

the function returns:

```text
None
```

It does not calculate a partial SMA.

### 11.3 Streaming Integration

The current implementation is a pure calculation function.

For future streaming integration, a rolling queue/window should be used so that the complete price history does not need to be recomputed for every event.

## 12. EMA

Exponential Moving Average applies greater weight to recent observations.

The formula is:

$$
EMA_t = \alpha P_t + (1-\alpha)EMA_{t-1}
$$

where:

$$
\alpha = \frac{2}{N+1}
$$

and:

* `P_t` = current price.
* `EMA_t` = current EMA.
* `EMA_(t-1)` = previous EMA.
* `N` = EMA period.

### 12.1 Initialization Rule

The Python analytics service initializes the EMA using the Simple Moving Average of the first `N` observations:

```text
EMA_initial = SMA(first N prices)
```

After initialization, each subsequent price uses:

```text
EMA = alpha * price + (1 - alpha) * previous EMA
```

This initialization rule is deterministic and is covered by unit tests.

### 12.2 Python Implementation

The Python analytics service provides:

```text
calculate_ema(prices, period)
```

The implementation:

1. Converts the input iterable to a list.
2. Validates that `period` is positive.
3. Validates that prices are present.
4. Returns `None` when fewer than `period` observations exist.
5. Initializes the EMA using the SMA of the first `period` prices.
6. Applies the standard EMA recurrence to subsequent observations.

### 12.3 Insufficient Data

If:

```text
number of prices < period
```

the function returns:

```text
None
```

No partial EMA is produced.

## 13. Volatility

The Python analytics service calculates rolling price-return volatility as the **sample standard deviation of simple returns**.

### 13.1 Simple Return

For consecutive prices:

$$
r_t = \frac{P_t-P_{t-1}}{P_{t-1}}
$$

where:

* `P_t` = current price.
* `P_(t-1)` = previous price.
* `r_t` = simple return.

### 13.2 Rolling Volatility

For a window containing `N` returns:

$$
\sigma =
\sqrt{
\frac{
\sum_{i=1}^{N}(r_i-\bar r)^2
}{
N-1
}
}
$$

where:

* `σ` = volatility.
* `r_i` = return `i`.
* `\bar r` = mean return.
* `N` = number of returns in the volatility window.

The implementation therefore calculates **sample standard deviation**, using `N - 1` as the denominator.

### 13.3 Period Definition

For volatility, `period` represents the number of returns included in the final volatility window.

Because every return requires two consecutive prices:

```text
required prices = period + 1
```

For example:

```text
period = 5
required prices = 6
```

### 13.4 Python Implementation

The Python analytics service provides:

```text
calculate_volatility(prices, period)
```

The implementation:

1. Converts the input iterable to a list.
2. Validates that `period` is positive.
3. Validates that prices are present.
4. Validates that every price is positive.
5. Returns `None` when fewer than `period + 1` prices exist.
6. Calculates simple returns.
7. Selects the latest `period` returns.
8. Calculates their mean.
9. Calculates squared deviations.
10. Calculates sample variance.
11. Returns the square root of the variance.

### 13.5 Single-Return Window

When:

```text
period = 1
```

only one return is available.

The implementation returns:

```text
0
```

because there is no dispersion among a single observation.

### 13.6 Insufficient Data

If:

```text
number of prices < period + 1
```

the function returns:

```text
None
```

## 14. Indicator Error and Data Availability Semantics

The analytics service distinguishes between **invalid input** and **valid input with insufficient historical data**.

### 14.1 Invalid Input

Invalid input raises `ValueError`.

Examples include:

* Non-positive indicator period.
* Empty required input.
* Non-positive prices where price positivity is required.
* Non-positive quantities.
* Mismatched VWAP input lengths.

### 14.2 Insufficient Historical Data

Insufficient but otherwise valid historical data does not represent an error.

The indicator returns `None`.

| Indicator  | Condition                      | Result         |
| ---------- | ------------------------------ | -------------- |
| VWAP       | Empty input                    | `ValueError`   |
| SMA        | Fewer than `period` prices     | `None`         |
| EMA        | Fewer than `period` prices     | `None`         |
| Volatility | Fewer than `period + 1` prices | `None`         |
| Volatility | `period = 1`                   | `Decimal("0")` |

This distinction allows the future analytics pipeline to represent unavailable indicators without generating misleading partial calculations.

## 15. Numeric Precision and Financial Representation

Financial price and metric calculations use Python's `Decimal` type in the analytics service.

The following values are represented internally as `Decimal`:

* Price.
* VWAP.
* SMA.
* EMA.
* Volatility.
* Realized PnL.
* Unrealized PnL.
* Equity.
* Peak equity.
* Drawdown.

The use of `Decimal` reduces unnecessary binary floating-point rounding in financial calculations.

The core Phase 3.3 indicator implementation does not require NumPy or Pandas.

### 15.1 JSON Serialization

The Python domain models convert `Decimal` values to strings when serialized using their `to_dict()` methods.

For example:

```json
{
  "price": "101.20",
  "vwap": "101.13",
  "sma": "101.10",
  "ema": "101.16"
}
```

This preserves the exact decimal representation across JSON serialization.

Integer quantities and positions remain numeric JSON values:

```json
{
  "quantity": 15,
  "position": 150
}
```

Consumers must therefore not assume that every financial field is represented as a JSON number.

## 16. Position Model

A simplified position can be represented as:

```text
position =
    cumulative_buy_quantity
    - cumulative_sell_quantity
```

Example:

```text
BUY 100
SELL 30
BUY 50

position = 120
```

A positive position represents net long quantity.

A negative position represents net short quantity.

A zero position represents no net quantity.

The complete position-management implementation is part of the planned risk and portfolio analytics work.

---

## 17. PnL

For a simplified mark-to-market model:

```text
unrealized_pnl =
    position * (current_price - average_entry_price)
```

The exact realized-PnL calculation depends on the selected accounting method.

Candidate accounting methods include:

```text
FIFO
Weighted Average Cost
```

The production implementation must select one deterministic method and document it as part of the analytics/risk contract.

The PnL model is not part of the Phase 3.3 technical-indicator implementation.

---

## 18. Risk Model

Initial risk metrics include:

* Gross exposure.
* Net exposure.
* Position size.
* Equity.
* Peak equity.
* Drawdown.
* Maximum drawdown.

### 18.1 Drawdown

Absolute drawdown is:

$$
Drawdown = PeakEquity - CurrentEquity
$$

Percentage drawdown is:

$$
Drawdown\% =
\frac{PeakEquity-CurrentEquity}{PeakEquity}
\times 100
$$

The Python `AnalyticsResult` model requires:

```text
peak_equity >= equity
drawdown >= 0
```

The complete risk-management implementation remains planned for a later analytics phase.

## 19. Event Contract Versioning

Every externally consumed event contract should include a schema version once protocol compatibility becomes necessary.

Example:

```json
{
  "schema_version": "1.0",
  "event_type": "TRADE"
}
```

Schema versioning must be independent of the application version.

Backward-incompatible contract changes require a new major schema version.

Backward-compatible additions may be introduced using optional fields.

Consumers should be designed to tolerate unknown fields where safe.

## 20. Serialization Rules

### 20.1 JSON

The MVP JSON representation follows these rules:

* UTF-8 encoding.
* No comments.
* ISO-8601 timestamps.
* UTC timestamps for externally transmitted events.
* Integer quantities remain JSON numbers.
* Financial `Decimal` values serialized by the Python domain models are represented as strings.
* `None` values may be represented as JSON `null` where the contract permits them.
* Unknown fields should be ignored by tolerant consumers where safe.

### 20.2 Socket Framing

For socket-based streams, the transport layer uses length-prefixed JSON frames:

```text
4-byte big-endian payload length
+
JSON payload
```

The framing protocol is transport-level behavior and is separate from the logical event schema.

### 20.3 Timestamp Format

Externally transmitted timestamps use ISO-8601 UTC.

Example:

```text
2026-09-07T12:00:02.000Z
```

The Python domain models internally use Python `datetime` values and serialize them using ISO-8601 formatting.

## 21. Python Domain Model Mapping

The current Python analytics service maps the logical event contracts to immutable domain models.

| Event / Result   | Python Model      | Event Type         |
| ---------------- | ----------------- | ------------------ |
| Market tick      | `Tick`            | `MARKET_TICK`      |
| Executed trade   | `Trade`           | `TRADE`            |
| Analytics output | `AnalyticsResult` | `ANALYTICS_UPDATE` |

The models are implemented as frozen dataclasses with slots.

Their primary responsibilities are:

* Represent domain data.
* Enforce basic domain invariants.
* Preserve financial precision using `Decimal`.
* Provide JSON-friendly dictionary serialization.

Business orchestration, socket ingestion, streaming pipelines, and publishing remain separate concerns.

## 23. Protobuf Migration

A future `.proto` model should represent the same logical concepts:

* Enumerations.
* Order.
* Trade.
* Book update.
* Market tick.
* Analytics update.
* Simulation status.
* Schema version.

The wire representation may change, but the meaning of the fields and calculations must remain consistent.
